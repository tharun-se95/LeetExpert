Stop sorting to check anagrams.

Caption
"listen" and "silent": same letters? 🧩
Most people sort both words and compare. That's O(n log n).

Think Scrabble. You wouldn't alphabetize two racks of tiles. You'd keep a tally:
+1 for every tile in the first rack, −1 for every tile in the second.
Every row back at zero means the same tiles.

In code: return False if the lengths differ; counts is the tally sheet (a dict from letter to number); +1 for each letter of s, −1 for each letter of t; then every count must be 0. One pass: O(n).

Our test run on 1,000,000 letters (Python): sorted() 215 ms, Counter 55 ms. Counting took about a quarter of the time.

Warehouses reconcile stock the same way: +1 per box in, −1 per box out.

⚠️ The classic 26-slot array only covers a–z. Give it "café" and Python raises IndexError: list index out of range, while JavaScript quietly returns false. Beyond a–z, count with a hash map.
⚠️ Never compare sets: set("aacc") == set("ccac") is True, but they aren't anagrams. Counts matter.

You've got a fifteen-dollar gift card. Spend every cent on exactly two things.

Caption
$15 gift card. Two items. Every cent. 🎁
The menu is sorted: $1 $3 $4 $5 $7 $8 $9.

Trying every pair takes 21 checks. With 1,000 items, it's 499,500.

Two pointers: put one finger on the cheapest item and one on the priciest.
Too low? Even the priciest item can't lift the cheapest one to $15, so cross the cheapest off.
Too high? The priciest item can't fit with anything that's left, so cross it off.

$1+$9, $3+$9, $4+$9, $5+$9, $7+$9 (too high), $7+$8 = $15. That's 6 checks instead of 21: O(n) time, O(1) memory.

Databases join sorted tables the same way (a merge join): one pointer per table, with no nested loop over every pair.

⚠️ It only works on sorted input. Stop when the fingers meet (`left < right`), or you'll buy the same item twice.

"Next greater element" has a shape.

Caption
For each number, find the first bigger number to its right: [2, 1, 5, 3]. Checking to the right of every number is O(n²).

Picture a concert 🎤: once someone tall stands in front of you, everyone shorter behind them is blocked for good. Only taller people ever matter again.

The stack keeps the numbers still waiting, biggest at the bottom:
2 arrives → push. 1 arrives → push. 5 arrives → pop 1 (answer 5), pop 2 (answer 5), push 5. 3 arrives → push. At the end, 5 and 3 keep −1.

def next_greater(nums):
    answer = [-1] * len(nums)
    stack = []                      # indexes, not values
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] < x:
            answer[stack.pop()] = x
        stack.append(i)
    return answer

Each index goes in once and comes out at most once: O(n). Our test run on 10,000 numbers (Python): 953 ms checking right of each vs 0.6 ms with the stack.

⚠️ The trap: store values instead of indexes, and when you pop you don't know where the answer goes. Look it up with index() and duplicates break it: [1, 1, 3] → [3, −1, −1].

This removes the even numbers. Or does it?

Caption
An AI wrote this in two seconds. It passes the sample test. Would you ship it? 🤔

for n in nums:
    if n % 2 == 0:
        nums.remove(n)

[1, 2, 3] → [1, 3] ✓
[2, 4, 6, 7] → [4, 7] ✗ (4 is even, and it survived)

Why: the for loop walks by position, and the position moves forward every time. remove() deletes the value and shifts everything after it one step left, so the next item lands in the slot you just checked, and the loop skips it. It's like checking tickets along a row of seats while everyone slides left under your finger.

Fix 1: don't edit the list you're reading. Build a new one:
return [n for n in nums if n % 2 != 0]

Fix 2, in place: a read pointer and a write pointer. Copy each keeper to write and move write forward. Write never passes read, so nothing unread is overwritten. Then del nums[write:].

And even the version that works (loop over a copy, remove from the original) is O(n²). Our test run on 100,000 numbers: 7,972 ms vs 4 ms for the new list.

Python raises "RuntimeError: dictionary changed size during iteration" for a dict. Lists and JavaScript arrays just skip, silently.

for right in range(len(nums)):
    total += nums[right]

        best = min(best, right - left + 1)

    if n < 2:
        return n
    if n in memo:            # already solved: no subtree at all

    memo[n] = fib(n - 1, memo) + fib(n - 2, memo)
    return memo[n]

Each value from 0 to n is computed once. fib(40) now takes 79 calls: O(n). In our test run it took 7 microseconds.

Carousel · 10 slides · media not uploaded yet · RC-MONOTONIC-STACK

"Next greater element" has a shape.

Caption
For each number, find the first bigger number to its right: [2, 1, 5, 3]. Checking to the right of every number is O(n²).

Picture a concert 🎤: once someone tall stands in front of you, everyone shorter behind them is blocked for good. Only taller people ever matter again.

The stack keeps the numbers still waiting, biggest at the bottom:
2 arrives → push. 1 arrives → push. 5 arrives → pop 1 (answer 5), pop 2 (answer 5), push 5. 3 arrives → push. At the end, 5 and 3 keep −1.

def next_greater(nums):
    answer = [-1] * len(nums)
    stack = []                      # indexes, not values
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] < x:
            answer[stack.pop()] = x
        stack.append(i)
    return answer

Each index goes in once and comes out at most once: O(n). Our test run on 10,000 numbers (Python): 953 ms checking right of each vs 0.6 ms with the stack.

⚠️ The trap: store values instead of indexes, and when you pop you don't know where the answer goes. Look it up with index() and duplicates break it: [1, 1, 3] → [3, −1, −1].

Fibonacci in three lines. What does fib(30) cost?

Caption
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

Clean, correct, and it passes every small test. Would you ship it? 🤔

fib(30) makes 2,692,537 calls. fib(40) makes 331,160,281. In our test run (Python), fib(40) took 14.5 seconds.

Why: draw the calls for fib(5). Every call splits in two, and the same questions come back. fib(3) runs twice, fib(2) three times, fib(1) five times. That's 15 calls to answer 6 different questions, and each repeat redoes its whole subtree: O(2ⁿ).

The fix is to remember every answer:

def fib(n, memo=None):
    if memo is None:
        memo = {}
    if n < 2:
        return n
    if n in memo:            # already solved: no subtree at all
        return memo[n]
    memo[n] = fib(n - 1, memo) + fib(n - 2, memo)
    return memo[n]

Each value from 0 to n is computed once. fib(40) now takes 79 calls: O(n). In our test run it took 7 microseconds.

⚠️ One catch: it's still recursion. A memoized fib(1000) crashes Python with "RecursionError: maximum recursion depth exceeded".

Watch binary search throw away half.

Caption
Find 9 in [1, 3, 5, 7, 9, 11, 13]. 📖 Do what you'd do with a paper dictionary: open the middle, keep one half, ignore the other.

mid = 7 < 9 → everything up to 7 is too small. Gone.
mid = 11 > 9 → 11 and everything after it. Gone.
mid = 9 → found, in 3 checks.

def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = lo + (hi - lo) // 2
        if arr[mid] == target: return mid
        elif arr[mid] < target: lo = mid + 1
        else: hi = mid - 1
    return -1

Each check halves the range: O(log n). A million sorted numbers take at most 20 checks. A billion, 30.

⚠️ The classic bug: lo = mid instead of mid + 1. Search [1, 3] for 3: mid stays 0 and lo stays 0, forever.
⚠️ It only works on sorted data, or anything where one comparison tells you which half to drop.

Answer any range sum in O(1).

Caption
nums = [2, 4, 1, 5, 3]. What's the sum from index 1 to 3? 4 + 1 + 5 = 10.
Now answer 10,000 of those. Adding each range from scratch costs up to O(n) every time.

Think of a car's odometer: it only shows the total since the car was new. Any trip = end reading − start reading. You never re-drive the trip. 🚗

A prefix array is that odometer: 0, 2, 6, 7, 12, 15.

def build_prefix(nums):
    prefix = [0] * (len(nums) + 1)   # prefix[0] = 0, the sum of nothing
    for i, x in enumerate(nums):
        prefix[i + 1] = prefix[i] + x
    return prefix

sum(l..r) = prefix[r + 1] − prefix[l]
1..3 → 12 − 2 = 10. 2..4 → 15 − 6 = 9. One subtraction, however wide the range.

Our test run, 10,000 queries on 100,000 numbers (Python): 4.96 s summing each range vs 6.1 ms with a prefix array, build included.

⚠️ Only for an array that doesn't change: update one value and every later total is stale.
⚠️ Off-by-one: prefix[r] − prefix[l] drops nums[r] (7 − 2 = 5, not 10).
