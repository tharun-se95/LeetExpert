## Caption

Insertion sort is O(n²). Except when it's O(n). Its real cost is how out of order your data is.

Insertion sort takes the next element, shifts the larger ones right, and drops it into place.

Reverse-sorted input is the worst case: [5, 4, 3, 2, 1] takes 1 + 2 + 3 + 4 = 10 shifts, and 1,000 reversed elements take 499,500.

Already sorted? 0 shifts and 999 comparisons, one per element. With 10 neighbouring pairs swapped: 10 shifts.

Every shift fixes exactly one inversion (a pair that's out of order), so the work is O(n + I), where I is the number of inversions. That's why it survives in practice: real data is often almost sorted.

Where have you seen insertion sort hiding inside a faster sort? 👇

## Alt text (per slide)

**Slide 1.** Cover. Sorting. Insertion sort is O(n²). Except when it's O(n). Its real cost is how out of order your data is.

**Slide 2.** The code. Shift the larger ones right Python code: def insertion_sort(arr: list[int]) -> None: / for i in range(1, len(arr)): / key = arr[i] / j = i - 1 / while j >= 0 and arr[j] > key: / arr[j + 1] = arr[j] / j -= 1 / arr[j + 1] = key. Take the next element, shift larger elements right, and drop it into its place.

**Slide 3.** The worst case. [5, 4, 3, 2, 1] Shifts: 1 + 2 + 3 + 4: 10. Reverse-sorted input: each insertion shifts all the way back. The triangular sum, O(n²).

**Slide 4.** Same code, 1,000 elements. It depends on the input Reverse-sorted: 499,500 shifts. Already sorted: 0 shifts · 999 comparisons. Sorted, with 10 neighbouring pairs swapped: 10 shifts.

**Slide 5.** The real measure. Inversions An inversion is a pair that is out of order relative to each other. Every shift resolves exactly one. So the total work is O(n + I), where I is the inversion count: how far the input is from sorted, not n outright.

**Slide 6.** Why it survives. Real data is often almost sorted A new log entry appended to a sorted log. One out-of-place card in a hand. On input like that, the inner loop's condition fails almost immediately, every time.
