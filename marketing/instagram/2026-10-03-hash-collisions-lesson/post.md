## Caption

What happens when two keys hash to the exact same slot?

With 4 buckets, 10 and 18 both land in slot 2. Collisions aren't a bug in your hash table. They're guaranteed.

Separate chaining: each bucket holds a list. Insert appends to that list; lookup scans only that one list.

That's why "O(1)" is an average. Put 100 keys that all hash to slot 4 into one table and finding the last one scans 100 entries. Spread the same number of keys out and it's 1.

Doubling the table helps, statistically: 3 and 7 split apart at 8 buckets, but 10 and 18 still share slot 2.

Did you know the O(1) was an average? 👇

## Alt text (per slide)

**Slide 1.** Cover. Hash Tables. Two keys, one slot. Now what? Nobody gets turned away. The slot grows a chain.

**Slide 2.** The collision. 10 and 18 both land in slot 2 A table with 4 buckets files a key under key % 4. Two different keys, one address. Sooner or later it is guaranteed to happen.

**Slide 3.** The fix: chaining. Each bucket holds a list Python code: def put(self, key, value): / chain = self.buckets[key % len(self.buckets)] / for entry in chain: / if entry[0] == key: / entry[1] = value / return / chain.append([key, value]). Insert appends to that bucket's list. Lookup scans only that one list, never the whole table.

**Slide 4.** Why it is still fast. O(1) on average The cost of any operation is the length of one chain. Under uniform hashing, the expected chain length is the *load factor*: entries per bucket. Keep it bounded by resizing and the expected work stays constant.

**Slide 5.** The catch. 100 keys, all for slot 4 Entries scanned to find the last one: 100. Same number of keys, spread out: 1. "Hash lookup is O(1)" quotes the average case, not a guarantee.

**Slide 6.** Doubling the table. 4 buckets become 8 3 and 7: shared slot 3: now slots 3 and 7. 10 and 18: shared slot 2: still slot 2, together. Doubling reduces collisions statistically, not individually.
